# DSH 科研项目映射：隔离验证记录

> 以下为 2026-11-17 临时预览阶段的历史验证记录。当前正式启动、项目会话和工具接入情况见 [DSH 原生工作区进度](DSH前端适配路线.md)。

项目界面以 DSH 原生工作区为基础；顶部全局新对话与项目会话分开。科研项目与 DSH 工作区的关联需要明确记录，不能根据当前页面或最近使用的项目推断范围。全局自动化、指定项目自动化以及对全部项目启用的插件也需要各自显式声明范围。

## 当前实现

`demo/api/dsh_workspace_map.py` 是尚未接入应用的实验性映射模块。调用方须显式提供数据库路径、项目根目录和可信的项目及 DSH 工作区查询函数。模块不创建或删除项目目录，不自动迁移现有项目或工作区；它只接受项目 ID 与该项目目录相符的原生工作区路径，并使用 SQLite 约束防止同一 profile 内的隐式改绑和重复绑定。读取已有映射时会再次核验项目和目录。

该模块本身不提供认证、用户授权或 MCP 权限隔离。实际接入必须由服务端查询可信的 DSH 工作区信息，在操作时确认权限；不得把浏览器传入的路径或项目 ID 直接作为可信授权依据。未绑定的工作区不能默认回退到最近项目。

## 2026-11-17 隔离验证

- 测试使用新建的临时 DSH profile、临时项目目录和临时 SQLite，未迁移或读取真实项目数据。
- DSH 原生 API 创建了测试工作区及会话。同一 DSH profile 重启后，原生侧栏仍显示该测试工作区，存储中的 workspace ID 与首次一致，且仍有会话关联。
- 使用该 workspace ID 在临时 SQLite 中写入项目映射，重新打开数据库后能读取对应项目。
- 映射测试覆盖持久化、幂等绑定、并发冲突、无效路径、项目或工作区变化后的拒绝处理。Windows 环境无法创建目录符号链接，因此符号链接测试跳过。
- 首次隔离 DSH 启动仍引用了用户 Documents 中的默认工作区路径；独立 `DSH_HOME` 不是文件系统沙箱。后续重启测试为 DSH 使用了临时用户目录。

测试结束后独立 DSH 和浏览器进程均已退出；临时 fixture 文件未清理。测试没有证明 `openWorkspace` 的异步调用已返回或目标会话被选中，也没有验证项目作用域 MCP、项目助手对话、真实用户项目或正式启动流程。

## 全局助手与命名接口的补充探针

- 在固定版 DSH 和隔离 profile 中，通过原生工作区 API 建立全局测试工作区，初始显示名设为 `goat`；原生重命名后，测试名称及同一 workspace ID 在进程重启后保留。这只验证 DSH 原生存储，不代表已与 LabWeave 的助手名称持久层同步。
- 一次仅存在于隔离测试插件的 `uiWorkspace.startSession` 包装探针中，插件自身发起的无参调用使用全局测试 ID，显式项目 ID 原样传递；两边的测试工作区均产生了会话。测试工作区选择浮层使侧栏顶部按钮处于不可点击状态，因此未验证真实顶部按钮是否经过同一包装，也不能视为用户要求的全局会话已接入。
- 包装卸载时有条件恢复原函数的策略尚未验证多插件嵌套、实例替换、加载时序和竞态。全局目录与 ID 的可信绑定、助手名与原生重命名的双向同步、项目作用域 MCP 和隔离权限均未完成；探针包装未加入正式配置。
- 助手名称代理在独立 DSH profile 与模拟本机业务服务中验证：授权读取和更新成功，匿名 GET/POST 被拒绝，伪造 Origin 和 Host 被拒绝，未注册的方法不可用。测试插件副本只替换了模拟服务的端口，未读取真实用户配置或密钥。
- 将固定版侧栏的本地副本保留官方包名和客户端模块 ID 后，隔离 Web 能启动；但仅通过 profile 安装、禁用原项并插入同名插件，服务返回的客户端代码仍不是测试副本。因此不能将该操作视为已替换上游侧栏。

## 接入前仍需完成

1. 使用持久且与旧 SDK 数据隔离的 DSH profile，验证原生工作区创建、选择、重启和会话恢复。
2. 设计并验证 DSH 工作区与已有项目的一对一绑定、失败恢复和显式关联流程，保留未关联的原生工作区及用户数据。
3. 把可信项目上下文及固定项目作用域 MCP 绑定到对应原生项目会话，并验证跨项目拒绝、全局会话不继承项目上下文、权限审批和恢复。
4. 在同一 DSH 界面内逐步接入助手、动态、点子、目标和资源库，再进行真实数据的端到端验收。
